## 全局规则卡：结算主游标与局部连锁队列

| 项目 | 规则 |
|---|---|
| 规则编号 | F015-R01 |
| 适用范围 | V0.2 及后续所有新增或重做的结算期骰子效果，以及离开市场时的离场骰主队列与其局部响应链；包括饲料、金币、吸附、临时小骰、成长、有效点、基础单骰分和触发标签。 |
| 核心原则 | 结算使用“左到右主游标 + 当前槽位局部连锁队列”。 |
| 强制性 | 已确认。后续任何结算规则卡、程序实现和验收样例不得绕过本规则。 |

### 执行流程

1. 摇骰结束后，按当时骰袋从左到右锁定本轮主结算骰的实例标识、顺序、自然点和本次可读状态。每颗锁定骰本轮最多执行一次自身结算；中途移除则轮到时跳过，中途新增的骰默认不取得本轮主结算次数。
2. 主游标从最左侧锁定骰开始，按锁定顺序向右推进。
3. 主游标到达某骰时，先完整执行该骰的自身结算效果。
4. 自身效果产生响应事件后，以当时仍在骰袋中的可见顺序从左到右扫描一次，收集所有合法响应，形成第一响应波。
5. 第一响应波从左到右执行。同一响应波尚未结束时，新产生的响应不得立即递归插队，统一进入下一响应波。
6. 当前响应波结束后，再按当时骰袋可见顺序从左到右扫描并执行下一响应波；如此循环，直到没有新响应。
7. 当前骰的全部响应波清空后，主游标才可以进入下一颗锁定骰。
8. 只有规则文字明确写明“全部骰子结算后”的效果才进入阶段末队列；阶段末同一时点的多个效果仍按骰袋从左到右处理。

### 队列排序默认值

- 默认排序键为“当前主骰顺序 → 响应波次 → 响应骰当前可见位置”。
- 每个响应波开始时只扫描一次当前骰袋；一波可以有多个响应，整条局部连锁可以有多波。
- 同一颗骰子对同一个响应事件最多响应一次；不同真实事件是否可再次响应，由骰子规则中的“每次 / 每轮一次”等边界决定。
- 同一颗骰子在同一波内有多个合法响应时，按该骰规则文字的声明顺序执行。
- 响应入队后若骰子已被移除或条件失效，执行到该响应时重新校验并记录跳过原因。
- 吸附、附属、临时小骰或宿主关系产生的响应，默认跟随其宿主所在槽位处理。
- 某颗骰子如果需要不同排序，必须在该骰自己的规则卡中写明，并通过审查；否则一律使用本默认值。

### 离开市场队列

1. 点击离开市场时，按当时骰袋从左到右建立离场主队列；默认每颗原有实体骰最多执行一次自身离场检查。
2. 当前离场骰先执行自身离场效果，再按本规则的分波方式清空它引发的全部响应；清空后才进入下一颗离场骰。
3. 多只满足条件的吸附龟按离场主队列依次化壳；前一只龟的化壳及全部响应必须结束后，后一只龟才开始化壳。
4. 吸附龟轮到时只检查当时紧邻的后一位；若该位置不是合法宿主则本次跳过，后续状态变化不会回头重新检查已经经过的龟。
5. 离场过程中新增的骰默认不进入本次离场主队列；只有骰子规则明确写明“加入当前离场队列”或“立即执行离场效果”时才作为例外，例如抢劫海盗。
6. 化壳发布的真实吸附事件必须统一按当前骰袋从左到右收集响应，不得按遗产龟、空舱龟、首领龟等效果类型写死跨骰优先级。

### 禁止行为

- 不允许先扫完整个骰袋，再统一回放本应属于某个槽位的局部连锁。
- 不允许只处理第一响应波就结束仍有合法新响应的局部连锁。
- 不允许新响应通过函数嵌套立即插到当前响应波剩余骰子之前；规则层允许连锁，程序层必须使用可追踪的分波队列。
- 不允许按效果类型建立隐藏的跨骰优先级；除非规则卡明确例外，同一波始终以骰袋位置为准。
- 不允许后侧槽位自己的“结算时”效果因为前侧连锁而提前自发触发；只有被当前连锁明确点名的响应可以提前进入队列。
- 不允许预览写入长期饲料、金币、成长、吸附或存档状态。
- 不允许结算展示层重新调用真实结算、重新随机、重复写钱包或重复入档成长。

### 已确认边界案例

- 肉猪的“饲料效果翻倍”是效果计数翻倍，不视为第二次获得饲料，因此不会因为翻倍本身再次触发“获得饲料时”的响应。
- 如果某槽位的效果让多颗骰子获得饲料，所有由该槽位引发的饲料响应和后续响应都必须在当前局部队列中结清，再进入下一槽。
- 三只小猪这类读取“其它骰子总饲料”的结算骰，只在主游标到达自己槽位时读取当时已经结清的状态；它不会提前读取后续槽位尚未自发结算的收益。
- 若第一响应波中的左二和左五都响应主骰，而左二又产生了左四可响应的新事件，则先完成第一波的左二、左五，再在第二波执行左四。
- 离场顺序为“龟甲、宿主甲、龟乙、宿主乙”时，先完成龟甲化壳及其全部响应波，再处理龟乙；顺序为“龟甲、龟乙、宿主”时，龟甲本次跳过、龟乙化壳，之后不回头重查龟甲。

### UI 表达要求

- 结算演出要让玩家感知“当前槽位触发”和“局部连锁追加”是同一组事件。
- 短标签优先显示当前槽位来源，例如 `槽2 养猪`、`连锁 贪吃`、`饲料 +1`。
- 局部连锁结束后，才切换高亮到下一槽，避免玩家误以为全部骰子同时触发。

### 连锁诊断日志

- 开发和内部试玩构建必须默认打印真实结算连锁日志到 Unity Console 与 `Player.log`；正式发布是否关闭详细日志由构建配置决定。
- 日志必须来自真实规则执行层，不能由动画或展示事件反推。加速、跳过动画或关闭表现不得改变日志顺序和最终状态。
- 每条局部连锁使用稳定的 `chainId` 和单调递增的 `seq`。每条记录至少包含：阶段、主骰原始槽位与实例标识、响应波次、事件类型、来源骰、响应骰或目标骰、执行结果、状态变化；跳过时必须包含原因。
- 至少打印 `chain_begin`、`root_begin`、`wave_scan`、`response_enqueue`、`response_execute`、`state_delta`、`response_skip`、`wave_end`、`root_end` 和 `chain_end`。
- 程序必须设置只用于防故障的连锁事件安全上限；触及上限时停止该异常连锁并打印 `guard_abort`、队列快照和相关骰子实例，不把上限包装成正常玩法规则。

### 程序验收要求

- 真实结算层需要有可追踪的主游标和局部队列边界。
- 测试样例必须覆盖：前槽触发多颗饲料、肉猪翻倍不二次触发、贪吃猪响应、第一波产生第二波、第二波不插队第一波、后槽自身效果不提前触发、三只小猪读取当前已结清状态。
- 离场测试必须覆盖：两只可化壳龟按顺序化壳、每次化壳清空响应后才处理下一只、前置龟不回查、明确加入队尾的新骰例外，以及不同类型响应骰仍按位置排序。
- Play Mode 验证必须保存一份完整连锁日志，并能仅凭 `chainId / seq / wave / source / target / delta` 还原实际执行顺序和关键状态变化。
- 展示事件只能消费已提交的队列结果，不得再次改变真实结算。
